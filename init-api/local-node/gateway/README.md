# Подготовка удалённого шлюза

Шаблоны сами по себе не являются активной установкой. Поддержка Timeweb
18.10.2026 в 02:25 подтвердила допустимость описанной схемы; регистрацию
рекомендует из-за возможной фильтрации протоколов. Владелец затем выбрал
продолжить с VPN. Это не гарантия доступности и не юридическое заключение.
Школьная база пока работает в облаке; этот каталог её не переносит.

На VPS и Pi включён WireGuard, ровно один peer на каждой стороне; закрытые
ключи созданы отдельно и не выгружались. Firewall VPS установлен отдельной
таблицей с закрытым forward и сохранением SSH, DHCP и мониторинга Timeweb.
Firewall Pi ограничен новым интерфейсом, LAN не меняет. Общие маршруты,
NAT и конфигурация других сервисов не менялись. HAProxy установлен из Debian,
публичные frontend включены для school-2036.gbousecurity.ru, сертификат
Let's Encrypt выпущен на Pi. Пока все публичные пути дают maintenance 503;
рабочий API не открыт. Проверять текущий статус в L05.

Предлагаемый транспорт: Raspberry -> WireGuard -> Timeweb VPS.
Браузер/Android -> TLS -> HAProxy (TCP, без расшифровки) -> Raspberry Caddy.
Ключ сертификата и база остаются на Pi. На VPS не устанавливать школьный API.

Адреса 10.77.203.1/32 (VPS) и 10.77.203.2/32 (Pi) сначала проверить на
конфликт с сетями обоих узлов. AllowedIPs содержит только адрес второго
участника: нет default route, доступа ко всей LAN или интернет-прокси.
IP forwarding, NAT/masquerade и port-forward домашнего роутера не нужны.

Заменить все `__...__` вручную при установке. Закрытые WireGuard-ключи
генерировать отдельно на каждом узле с umask 077, не передавать через чат
или Git. Файлы /etc/wireguard — root-only, конфигурация 0600.

`haproxy.cfg.example` требует отдельного DNS-имени и проверки `haproxy -c`
на фактической установленной версии. До проверки не копировать поверх
рабочего конфига. TCP 443 принимает только выбранный SNI; другие имена
отклоняются. Порт 80 передаёт на Pi только ACME challenge выбранного Host,
остальные запросы этого Host перенаправляет на фиксированный HTTPS URL.
Access/payload logging не включён. TCP health check не проверяет сертификат:
сертификат/имя/цепочку обязаны проверять конечные клиенты.

До открытия портов нужен firewall с сохранением рабочего SSH и необходимых
служб провайдера. Не выполнять `flush ruleset` и не заменять чужие правила.
8081/8765/2019 не публиковать. На Pi порт 8081 остаётся loopback-only.
Публичный Caddy site доступен через адрес туннеля. Слушатели Caddy общие с LAN;
LAN site первым правилом route отклоняет TCP-источник шлюза, чтобы HTTP Host
не позволял обойти публичный maintenance. Локальный CA не заменяется.

`Caddyfile.maintenance.example` — фактически проверенная промежуточная
конфигурация. Сначала validate, сохранить текущий файл для отката, затем reload.
Не снимать maintenance до защиты входа и свежего переноса. `-Alt-Svc` нужен,
поскольку TCP-шлюз не передаёт HTTP/3. Таймер `gbou-tls-clock-guard` требует
скрипт tools/pi_tls_clock_guard.py в /usr/local/sbin/gbou-tls-clock-guard.py;
восстанавливает только истёкший LAN leaf после синхронизации часов.

Сначала staging/диагностика без персональных данных, затем проверка защиты
входа и ролей. Финальный перенос — только по ../CUTOVER.md со свежим снимком.
При недоступности Pi шлюз не должен возвращать старые облачные списки.
