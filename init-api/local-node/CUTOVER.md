# Порядок перехода одной школы на Raspberry Pi

Этот документ — подготовка операции. Ничего из него не выполнялось.
Переключение проводится только когда Raspberry, USB, HTTPS и устройства
учителей/охраны доступны для проверки. Действующий сервис сейчас не
останавливать: без локального узла школа останется без заявок.

## 1. До окна переноса

- Установить локальный API, настроить HTTPS `gbousecurity.local` и доступ
  с устройств школы без выхода API в публичный интернет.
- Подключить отдельную USB-флешку по UUID; проверить работу ежедневного
  таймера и восстановление снимка в отдельный файл.
- Применить миграцию `010` в центральном сервисе, выдать отдельный ключ
  узла школы и проверить `node/config`.
- Передать на Raspberry актуальную школьную web-сборку, проверить вход и
  работу в тестовом режиме. Нативный Android потребует отдельной настройки
  локального адреса и доверия к сертификату до перевода пользователей.
- Зафиксировать ID школы и число школ/корпусов/администраторов/учителей/
  охранников/классов/учеников/заявок. Проверить свободное место на SD и USB.
- Подготовить резервную копию центральной PostgreSQL и документировать её
  срок хранения. USB-копия не заменяет эту предоперационную страховку.

## 2. Короткая пауза школьных изменений

Включить `MIGRATION_FREEZE_WRITES=true` при `DEPLOYMENT_MODE=legacy` и
дождаться, что новые заявки и изменения школьных справочников получают
сообщение 503 «Школьные изменения временно приостановлены для переноса
данных». Центральный кабинет остаётся доступен. Согласовать время с
учителями и охраной; работа без системы в этот период должна иметь
утверждённый бумажный/организационный порядок.

## 3. Копия и проверка

- Создать зашифрованный архив ровно одной школы с помощью
  `scripts.local_node export-school`.
- Передать архив по защищённому каналу и импортировать в пустую локальную
  SQLite. Повторный импорт в непустую базу запрещён.
- Сравнить количества таблиц на обеих сторонах и выборочно сверить записи,
  не публикуя ФИО детей в чатах и открытых журналах.
- Запустить синхронизацию корпусов/администраторов, проверить вход школьного
  администратора, учителя и охраны, создание и выпуск тестовой заявки.
- Создать USB-копию и восстановить её в **отдельную** базу, проверить
  `integrity_check` и вход в тестовом окружении.

Если хотя бы одна проверка не прошла, **не включать cloud**, снять паузу
`MIGRATION_FREEZE_WRITES=false`, устранить проблему и повторить экспорт в
новом окне. Старую зашифрованную копию хранить защищённо до решения.

## 4. Переключение

- Перенастроить киоск охраны на локальный `127.0.0.1:8081` и проверить
  очередь/выпуск без интернета.
  В `/etc/gbou-kiosk.conf`: `GBOU_API_BASE=http://127.0.0.1:8081/api/v1`
  и `GBOU_KIOSK_LOCAL_MODE=1`. Установить версию server.py с fail-closed
  проверкой адреса и запретом API redirects; unit требует файл конфигурации.
  Пропажа адреса/конфига не должна возвращать киоск на облачный API.
- Перевести устройства учителей/администратора на локальный HTTPS-адрес;
  Android APK не переключать, пока для него не готов локальный адрес и TLS.
- Только после этого установить TimeWeb `DEPLOYMENT_MODE=cloud`. Облачный
  API перестанет публиковать школьные маршруты и принимать школьные роли.
- Опубликовать центральную web-сборку с `GBOU_CLOUD_ONLY=true`; убедиться,
  что суперadmin управляет школами/корпусами/администраторами, а сотрудники
  школы работают локально.
- Наблюдать за локальным узлом, USB-копиями и синхронизацией несколько дней.

## 5. Отдельное решение об очистке TimeWeb

`DEPLOYMENT_MODE=cloud` **не удаляет** старые персональные записи из
PostgreSQL. Очистка таблиц учителей, охраны, классов, учеников, заявок,
категорий, школьных журналов и их сессий требует отдельного подтверждения
после проверенного переноса и проверки периода хранения. Отдельно выяснить,
сколько TimeWeb хранит собственные резервные копии и как удаляются старые
снимки; SQL-удаление в рабочей базе не стирает резервные копии провайдера.

## Откат

До первого локального рабочего изменения можно вернуть `legacy` и снять
паузу. После появления новых локальных заявок простой возврат старой
облачной базы создаст две расходящиеся истории. В этом случае сначала
нужен план обратного переноса/сверки, а не переключение одной переменной.
