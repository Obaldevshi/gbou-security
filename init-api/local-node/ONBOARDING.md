# Несколько школ и Raspberry

## Адрес и владение базой

Номер236 → `236.gbousecurity.ru`. Адрес резервируется при создании школы;
для существующей — при первом открытии «Адрес и устройства». При повторении
номера используется236-ID; переименование школы и замена SD/Pi адрес не меняют.
Это DNS label, не отдельная платная регистрация домена. Основной сайт и
старый school-2036.gbousecurity.ru сохраняются. Резервирование в БД само по
себе не выдаёт сертификат и не открывает сеть.

В каждой школе один primary writer. Все корпуса/дочерние киоски работают
с этой базой по обычному HTTPS. Terminal не получает node/config, хеши
паролей администраторов, sync key или собственную рабочую SQLite. Сама
машинная регистрация не заменяет обычный вход охранника и не отменяет его
права: отзыв терминала не является отзывом пользовательского токена.

## Одноразовая настройка центра/шлюза — только после согласия владельца

1. Применить аддитивную миграцию011, опубликовать backend/frontend. Feature
   flag `SCHOOL_DEVICES_ENABLED=false` по умолчанию: старый node/config и
   рабочая школа не затрагиваются.
2. Назначить `SCHOOL_DOMAIN=gbousecurity.ru`, публичный WireGuard key и
   endpoint существующего шлюза. Сгенерировать отдельный длинный credential
   для read-only gateway-manifest: в API только SHA256, на VPS файл0600.
   Это НЕ ключ школы и не SECRET_KEY. Выдача ключа — отдельное подтверждение.
3. Один раз добавить wildcard A `*.gbousecurity.ru` на91.198.220.13, TTL300.
   Root A и явные существующие поддомены не заменять. Не покупать новый IP,
   wildcard SSL или отдельныйVPS. HAProxy отклоняет любой невыданный SNI.
4. Установить gateway/managed_routes.py и reconcile.py в `/opt/gbou-gateway`.
   Создать `/etc/gbou-gateway/managed.json`0600:

   ```json
   {
     "manifest_url": "https://obaldevshi-gbou-security-ac8a.twc1.net/api/v1/devices/gateway-manifest",
     "token_file": "/etc/gbou-gateway/manifest.token",
     "apply_approved": false,
     "preserved_routes": [
       {"hostname": "school-2036.gbousecurity.ru", "tunnel_ip": "10.77.203.2"}
     ]
   }
   ```

   Сначала `python3 /opt/gbou-gateway/reconcile.py` dry-run. Только после
   проверки HAProxy2.6, изоляции и отката владелец разрешает apply_approved;
   затем установить одноимённые systemd service/timer. Worker root нужен для
   WG, приватный ключ шлюза никуда не передаётся. WGpeer AllowedIPs — только
   назначенный10.78.x.x/32, никакихdefault routes/пересылки между школами.
   ВнешниеTLSprivatekeys создаёт Caddy на каждойPi, неVPS.

Сбой HTTPS/schema/manifest не изменяет рабочую конфигурацию. Не добавлять
таймеру доступ к полной Timeweb API: wildcard позволяет обойтись без него.
Пока включение не согласовано, candidates/код не являются действующей
автоматизацией. На18.10.2026 live gateway обслуживает одну прежнюю школу.

## Новая главная Raspberry

1. Raspberry Pi OS Lite, проверенное питание, SD/USB, точный школьный ID.
   Полный API установить штатным local-node/install.sh. Для регистрации
   нужен системный wireguard-tools (официальный apt), Python3.11+.
2. В chief console открыть школу → «Адрес и устройства» → приглашение primary.
   Код10мин, хранится вБД хешем. Не посылать код вчат, URL или аргументshell.
3. На новойPi выполнить:

   ```sh
   sudo python3 local-node/device_enroll.py --cloud https://obaldevshi-gbou-security-ac8a.twc1.net --role primary --label "Главный сервер"
   ```

   Ввести код в скрытом prompt. UUID и privateWGkey создаются только наPi;
   конфигурация0600 под/etc/gbou-device. Повтор запроса после потери HTTPответа
   идемпотентен в пределах срока приглашения. Не клонировать identity наSD.
4. `prepare_primary_network.py` создаёт и проверяет network-candidates,
   не меняя службы. Он требует защитить LANvhosts от фактическогоgatewayIP.
   Оператор проверяет Caddyfile/firewall и сохраняет старые конфиги перед
   установкой. Не запускать этот установочный сценарий на действующей2036.
5. Для НОВОЙ пустой школы подготовитьSQLite,USB и checkrestore. Node sync
   будет разрешён только после активации: скопировать device.token в
   `/etc/gbou-local/node.token`0600/gbou-local, указатьschoolID. После активации
   выполнить `scripts.node_config enroll-empty`, проверить ролевой вход и
   USBbackup/restore, только затем допускать сотрудников. Не импортировать
   снимок другой школы. Для существующей школы нужен шагзамены ниже.
6. После явной активации изchief gateway-agent выставит peer/маршрут в течение
   минуты. Установить проверенные сетевыеcandidates, включить WG/firewall,
   Caddy получит публичный сертификат черезHTTP01. Проверить публичные
   ready/TLS/401, чужиероли403,LANHostbypass404 и закрытые8081/8765/2019/22.
   При ошибке оставитьпользователямmaintenance, неfallback вcloud.

## Замена primary: без двух рабочих баз

1. Создатьприлашение/зарегистрироватьpending новоеустройство. URL не меняется.
2. Организовать окно: остановить старый writer, сделать свежую зашифрованную
   USBкопию, проверитьrestore в отдельныйфайл и итоговыечисла/связи/роли на
   новойPi. СтаруюPi физически выключить или изолировать отLAN итуннеля.
   Одна лишь потеряheartbeat НЕ доказательство выключения.
3. Chiefподтверждает две галочки: старыйprimary остановлен, новаябаза/копия
   проверены. Ожидаемоепоколение защищает отконкурентнойактивации. Новыйprimary
   становитсяединственным active,старыеdevice/synckeys отзываются. Дочерние
   устройстваиспользуют прежнийURL. Автоматическоймиграции БД эта кнопка неделает.
4. ПроверитьHTTP/роли/USB; старуюSD нестирать доотдельногорешения. Обратное
   переключение после новыхзаписей требует сверкиданных, неоткатаDNS.

## Дочерний терминал

После установки существующего kioskпакета (без localAPI/SQLite) создатьinvite
terminal, выполнитьdevice_enroll.py с `--role terminal`, затем:

```sh
sudo python3 local-node/configure_terminal.py
```

Команда проверяет обычныйTLS/ready,отсутствие школьнойБД/API,активнуюрегистрацию,
делаетbackup kioskконфига ипереключаетего накороткийHTTPSшколы. Machine-token
вбраузер непередаётся. Войти обычным guardаккаунтом. Приотказеprimary все
терминалы теряют очередь; без отдельной офлайнсинхронизации этоожидаемо.

Для работы дочерних терминалов без интернета рекомендуется split DNS в
школьной сети: тот же публичный hostname разрешается во внутренний IP
главной Raspberry. Сертификат остаётся публично доверенным, приложение
не меняет адрес и не отключает проверку TLS. Это отдельная настройка
школьного DNS/роутера; текущий установщик её не выполняет. Пока split DNS
не настроен, дочерний терминал использует внешний шлюз и зависит от интернета.
