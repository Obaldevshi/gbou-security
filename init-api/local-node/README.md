# Локальный школьный узел: подготовка и безопасный перенос

Это **этап подготовки**, а не команда немедленно удалить облачную базу.
До согласованного переключения TimeWeb остаётся в `DEPLOYMENT_MODE=legacy`.
Одна Raspberry Pi 3 служит основным узлом школы; устройства охраны,
учителей и администратора обращаются к ней по школьной сети.

## Что хранится где

- SD-карта: `/var/lib/gbou-local/school.sqlite3` — рабочая база SQLite,
  `-wal` и `-shm` файлы рядом. Права ОС: только пользователь `gbou-local`.
- USB-флешка: `/mnt/gbou-backup/school-*.gbou` — зашифрованные снимки.
- Ключи/секреты: `/etc/gbou-local/api.env` и
  `/etc/gbou-local/backup.passphrase`; после выдачи ключа также
  `/etc/gbou-local/node.token`. Пароль резервных копий **обязательно**
  сохранить вне Raspberry в защищённом месте. Если SD сломается вместе с
  единственной копией пароля, USB-снимки восстановить невозможно.

Рабочая SQLite на SD пока не зашифрована: защита только правами ОС. Для
защиты при физической краже SD требуется отдельная настройка шифрования.

## Установка ПО (на Raspberry, после передачи полного каталога `init-api`)

```sh
cd init-api
sudo sh local-node/install.sh
systemctl status gbou-local-api.service
```

Установщик создаёт пустую базу и системные службы. Он **не импортирует**
личные данные, **не переключает** киоск, **не очищает** TimeWeb и **не
монтирует** флешку. Служба API слушает только `127.0.0.1:8081`.

## Флешка

Для надёжного ежедневного резервирования отформатировать отдельную USB-флешку
в ext4 (это стирает её содержимое; делается администратором отдельно),
узнать её UUID и добавить точную запись в `/etc/fstab`:

```text
UUID=<UUID_ИМЕННО_ЭТОЙ_ФЛЕШКИ> /mnt/gbou-backup ext4 nofail,noatime 0 2
```

После монтирования назначить владельца точки монтирования `gbou-local`,
проверить `mountpoint /mnt/gbou-backup` и вручную запустить:

```sh
sudo systemctl start gbou-local-backup.service
sudo systemctl status gbou-local-backup.service
```

Таймер работает ежедневно в 02:15. Отсутствие USB вызывает ошибку; копия
не должна незаметно остаться на SD. Периодически проверяйте свободное место
и пробное восстановление. Автоматического удаления старых копий пока нет.

## Перенос конкретной школы

Согласуйте короткое окно без новых заявок и изменений справочников.
Если во время экспорта кто-то продолжит менять заявки, возникнет расхождение:
экспорт является согласованным снимком на один момент времени, но не
переносит последующие изменения автоматически. Перед окончательным
переключением требуется повторный экспорт в согласованное окно.
На сервере с существующей базой и переменными API:

```sh
python -m scripts.local_node export-school --school-id <ID_ШКОЛЫ> --out /защищенный/путь/school.gbou
```

Пароль архива вводится интерактивно и не попадает в аргументы процесса.
Передайте архив на Raspberry по защищённому каналу, затем **в пустую базу**:

```sh
sudo su -s /bin/sh gbou-local -c 'set -a; . /etc/gbou-local/api.env; set +a; cd /opt/gbou-local-api; .venv/bin/python -m scripts.local_node import-school --in /защищенный/путь/school.gbou'
```

Используется уже защищённый файл `/etc/gbou-local/api.env`; `SECRET_KEY`
не попадает в историю оболочки. Архив должен быть доступен пользователю
`gbou-local` только на время переноса.
После импорта сравните напечатанные количества с экспортом и проверьте
работу всех ролей. Архив содержит персональные данные; не передавайте его
по открытым ссылкам и удаляйте только после успешной проверки и USB-копии.

## Синхронизация центральных настроек

После применения миграции `010_school_node_credentials` в центральном API
создайте ключ для конкретной школы командой на сервере:

```sh
python -m scripts.node_config provision --school-id <ID_ШКОЛЫ> --out /защищенный/путь/node.token
```

Содержимое ключа не выводится в журнал и не хранится открытым текстом в
центральной базе. Передайте файл на Raspberry защищённо, установите владельца
`gbou-local`, права `0600`, поместите в `/etc/gbou-local/node.token`, а в
`/etc/gbou-local/api.env` установите `GBOU_SCHOOL_ID=<ID_ШКОЛЫ>`.
Первую синхронизацию выполните вручную и сравните корпуса и администраторов:

```sh
sudo systemctl start gbou-local-sync.service
sudo systemctl status gbou-local-sync.service
sudo systemctl enable --now gbou-local-sync.timer
```

После этого узел запрашивает конфигурацию по исходящему HTTPS раз в пять
минут. При отсутствии интернета локальные учителя и охрана продолжают
работать на прежней конфигурации; изменения главного администратора не
применятся до восстановления связи. Локальная смена пароля школьным
администратором сохраняется; явный сброс главным администратором имеет
приоритет и отзывает доверенные сессии этого администратора.

## Доступ с телефонов и компьютеров

Локальный API **нельзя** публиковать наружу по HTTP. Образец конфигурации
`Caddyfile.example` рассчитан на `https://gbousecurity.local`: TLS и локальная
раздача Flutter web из `/var/www/gbou-local`. Нужно обеспечить разрешение
имени в школьной сети, установить корневой сертификат локального Caddy на
клиентские устройства и убедиться, что школьная сеть не изолирует клиентов.
Web-приложение, открытое с этого имени, автоматически выбирает локальный API.
Для финальных сборок предусмотрены флаги `--dart-define=GBOU_LOCAL_MODE=true`
для школьного web и `--dart-define=GBOU_CLOUD_ONLY=true` для центрального web:
первый скрывает редактирование корпусов у локального администратора, второй
убирает центральные ссылки на школьные отчёты и аудит. До переноса текущие
production-сборки не заменяются.
Установить готовую школьную web-сборку можно командой
`sudo sh local-node/install-web.sh /точный/путь/к/web`.
Инструкции Android и доверия к HTTPS: [CLIENTS.md](CLIENTS.md).
Пока web-сборка не скопирована на Raspberry и TLS не настроен, школьные
роли продолжают пользоваться прежним сайтом; переключать облако нельзя.

Киоск Raspberry после успешного импорта можно перенастроить на
`GBOU_API_BASE=http://127.0.0.1:8081/api/v1` в `/etc/gbou-kiosk.conf`,
затем перезапустить `gbou-kiosk.service`. Не делайте этого до проверки
локального API.

## Проверка восстановления

На отдельном носителе или тестовом устройстве (не поверх рабочей базы):

```sh
python -m scripts.local_node restore-to-file --in /mnt/gbou-backup/school-XXXX.gbou --out /защищенный/путь/recovery.sqlite3
```

Восстановление создаёт только новый файл и проверяет целостность SQLite.
Подмена работающей базы требует остановки службы и отдельной процедуры.

## Что ещё НЕ готово

- Автосинхронизация новых/изменённых корпусов и школьных администраторов
  реализована в коде, но ещё не установлена и не проверена
  на Raspberry и действующем TimeWeb.
- Маршрутизация Android и доверие к школьному CA реализованы; требуется
  проверка на реальном телефоне и сертификате Raspberry.
- Наличие актуальной Flutter web-сборки на Raspberry и настройка Caddy.
- Физическое удаление школьных персональных данных из TimeWeb после
  проверенного переноса и отдельного подтверждения.
- Контроль шифрования рабочей SD-карты. Статус USB/места/копий добавлен в
  локальный кабинет школы, но ещё не проверен на реальном Raspberry.

Не включайте `DEPLOYMENT_MODE=cloud` на production до завершения этих шагов.

## Новая школа без старой базы

Для новой школы экспорт не нужен: после выдачи ключа узла, указания ID школы
и установки API выполнить `python -m scripts.node_config enroll-empty`
с загруженным `/etc/gbou-local/api.env`. Команда получает только школу,
корпуса и администраторов. Учителей, охрану, классы и учеников создаёт
школьный администратор уже локально. Для существующей школы 2036 сначала
обязательно импортировать архив, иначе старые записи не появятся.

## Отзыв ключа узла

В центральном сервисе: `python -m scripts.node_config revoke --school-id ID`.
Это прекращает обновление настроек, но не стирает локальную базу и не
останавливает работу школы. Ротация: выдать новый ключ `provision` в новый
защищённый файл, затем передать на Raspberry; прежний ключ сразу недействителен.
