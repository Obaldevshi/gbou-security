## Сверка

- Префикс `/api/v1` сохранён; Flutter web на `gbousecurity.local` выбирает
  same-origin локальный API. На центральном сайте до переключения остаётся
  текущий облачный адрес из `assets/env/.env`.
- Главное меню школ теперь открывает тот же экран корпусов, но через
  `/system/schools/{id}/buildings`; школьный экран остаётся на `/school/buildings`.
- Схемы корпуса (`id,name,address,is_active`) совпадают для центрального и
  локального Flutter datasource; JSON snake_case совпадает.
- `node/config` и CLI синхронизации используют типизированную схему;
  `hashed_password` не выводится в пользовательском UI и не пишется в лог
  запросов. Ответ имеет `Cache-Control: no-store`.
- Ошибки FastAPI остаются в общем формате `status_code,message,detail,code`;
  существующий Flutter ErrorHandler используется для CRUD корпусов.
- PostgreSQL-миграция `010_school_node_credentials` продолжает `009`.
  Локальный SQLite создаётся отдельно из SQLAlchemy metadata; Alembic
  PostgreSQL-миграции на Raspberry не запускаются.
- Dockerfile и `entrypoint.sh` продолжают слушать `0.0.0.0:8080` в TimeWeb.
  В режиме `cloud` демо-школьные учётные записи больше не создаются.
- `DEPLOYMENT_MODE` перечислен в `.env.example`; локальные переменные и
  секреты создаёт `local-node/install.sh`, но реальные значения не коммитятся.

## Критические до включения `cloud`

1. Настроить в Android выбранный локальный HTTPS-узел и проверить его
   школьный CA на реальном телефоне. Есть импорт PEM и сверка SHA-256,
   смена подключения сбрасывает все локальные токены/PIN.
2. Flutter web-сборку необходимо разместить на Raspberry и настроить Caddy,
   локальное имя и CA на устройствах пользователей.
3. Центральная сборка должна использовать `GBOU_CLOUD_ONLY=true`:
   код скрывает «Отчёты» и «Аудит»; API блокирует их в режиме cloud.
4. Облачная PostgreSQL всё ещё физически хранит прежние персональные данные.
   Нужен проверенный перенос, USB-восстановление и отдельно согласованная
   очистка вместе с политикой хранения резервных копий TimeWeb.
5. Синхронизация, резервирование, роли и откат требуют ручной проверки на
   реальной Raspberry и в локальной сети школы.

## Ручная проверка после доступа к устройству

Экспорт/импорт: количества строк девяти таблиц совпадают; повторный импорт
запрещён. Синхронизация: добавить/переименовать/отключить корпус, сбросить
пароль администратору, проверить конфликт логина и отказ при неверном ключе.
Охрана/учитель: заявка, выпуск, история после перезапуска. USB: отсутствие
флешки даёт ошибку, наличие — зашифрованный снимок, восстановление в отдельную
SQLite проходит integrity check. Проверить узкий и широкий web-экран, кнопки
корпусов, светлую/тёмную тему, клавиатуру, нижний overscroll.

## Дополнительно проверено локально

- Профиль и смена пароля остаются доступными в cloud; request-events
  не обращается там к школьным таблицам.
- Импорт ограничен одной школой, пустой базой и внутренними внешними ключами.
- Архивы создаются без перезаписи существующего файла; восстановление
  не заменяет рабочую базу, проверяет integrity_check/foreign_key_check.
- USB должна быть на другой файловой системе: bind-mount SD от systemd
  не принимается как резервный носитель. Требует проверки именно на Pi.
- Администраторы, синхронизированные с отрицательными ID, не перезаписывают
  локальных учителей; новые локальные ID положительны.
- Установочные сценарии проверены `bash -n`; локальный набор зависимостей
  не устанавливает PostgreSQL/Gunicorn и не компилирует Rust на Pi молча.

# Предыдущая проверка API перед TimeWeb — E15

Дата: 2026-09-23
Результат на тот момент: контракт доверенных Android-устройств готов к миграции,
сборке и публикации. Эти результаты относятся к E15, **не к текущему L01/L02**.

## Сопоставление Flutter ↔ FastAPI (E15)

| Метод | Полный путь | Авторизация | Тело / параметры | Успешный ответ | Основные ошибки |
|---|---|---|---|---|---|
| POST | `/api/v1/auth/trusted-devices` | Bearer | `device_name`, 2–120 символов | `201`, устройство и однократно показанный `refresh_token` | `401`, `403 password_change_required/account_inactive/school_inactive`, `422` |
| POST | `/api/v1/auth/trusted-devices/refresh` | refresh-token, без Bearer | `refresh_token`, 40–256 символов | `200`, новый access-token, ротированный refresh-token, пользователь | `401 trusted_session_invalid/trusted_session_expired`, `403` |
| POST | `/api/v1/auth/trusted-devices/revoke-token` | refresh-token, без Bearer | `refresh_token` | `200`, идемпотентный отзыв | `422` |
| GET | `/api/v1/auth/trusted-devices` | Bearer | — | `200`, список активных устройств | `401`, `403` |
| DELETE | `/api/v1/auth/trusted-devices/{id}` | Bearer | целочисленный `id` | `200` | `401`, `404` |

- Retrofit использует те же пути относительно base URL `/api/v1`.
- Имена JSON совпадают: `refresh_token`, `trusted_device_id`, `expires_at`,
  `last_used_at`, `created_at`.
- Refresh-token имеет не менее 256 бит случайности, хранится в БД только как
  SHA-256 и вращается при каждом успешном обновлении.
- PIN состоит из четырёх цифр, не отправляется на API и хранится на Android
  только как производный хеш с отдельной солью в secure storage.
- После пяти локальных ошибок доверенная сессия удаляется с телефона; требуется
  обычный логин и пароль.
- Отключение пользователя/школы и обязательная смена пароля проверяются сервером
  при каждом refresh.
- Web не предлагает PIN и продолжает использовать обычный вход.

## Конфигурация и миграции E15

- Добавлена миграция `009_trusted_device_sessions`, следующая после
  `008_superadmin_password_recovery`.
- `.env.example` содержит `TRUSTED_DEVICE_EXPIRE_DAYS=30`, без секретов.
- Обязательные `DATABASE_URL`, `SECRET_KEY`, CORS и access-token настройки
  сохранены.
- Публичных HTTP-маршрутов восстановления суперадминистратора нет. Сброс
  выполняется только интерактивной CLI-командой в терминале сервера.
- `entrypoint.sh` проверяет БД, выполняет `alembic upgrade head` и запускает
  `uvicorn app.main:app --host 0.0.0.0 --port 8080`.
- `/health` и `/ready` не изменены.

## Ручной чек-лист после авто-деплоя E15

1. Убедиться, что миграция `009_trusted_device_sessions` выполнена.
2. Проверить `/ready` и вход каждой ролью.
3. На Android войти логином и паролем, создать PIN и перезапустить приложение.
4. Убедиться, что правильный PIN восстанавливает роль, а пять неверных попыток
   возвращают обычную форму входа.
5. Отозвать устройство в профиле и проверить повторный запрос логина и пароля.
6. На ширине телефона проверить окно выбора учеников и кнопку
   «Добавить ученика» над нижней навигацией.
7. Открыть `https://gbousecurity.ru/about/` и проверить статическую страницу.
